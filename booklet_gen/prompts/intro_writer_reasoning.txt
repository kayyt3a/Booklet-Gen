Return a single JSON object matching this schema exactly:

  "worked_example": {

    "answer": "The final answer.",
    "diagram_spec": null
  },
  "guided_examples": [
    {
      "question": "A second short example, a different trick of the same type.",

      "diagram_spec": null
    }

- mnemonic: a short memorable hook when one fits naturally, else null. Do not force it.
- guided_examples is the "we do" step: 1 to 2 more short examples the student works through WITH the tutor before working alone. The student FILLS THIS IN, so it is not a second demonstration: wrap every value they are meant to work out themselves in [[double square brackets]], and the booklet prints a ruled gap there for them to write in, with the value itself going to the answer key. Blank the RESULT of each step, never the letters, numbers or terms the question gives and never the words that explain the method: "Shift each letter back one: [[CAT]]" is right, "[[Shift]] each letter back one: CAT" and "Shift each [[letter]] back [[one]]" are both wrong. EVERY step that works something out ends in a blanked value, one or two of them, never none: a step whose result is already printed asks the child to read rather than to think. The `answer` field is blanked the same way. NO step may print the final answer as plain text, not even as a summing-up. "The rule is add 4, so the next term is [[21]], giving 21" hands the answer over two lines above the gap that asks for it and the exercise is finished before it starts; blank it in both places, or stop the step at the first one. Keep enough unblanked that the method is still readable: the child should be able to see WHAT to do at every step and have to work out only the value. The worked_example above must have NO [[ ]] at all, it stays fully solved.

CONTENT RULES
- Intro paragraphs: obey the LENGTH LIMITS in the user turn exactly. Explain the TYPE of question and the STRATEGY for spotting the trick, not the underlying arithmetic or vocabulary, which should be simple.
- Key points: the number and length are set by the LENGTH LIMITS. Punchy and strategy-focused (e.g. "Read every word before you start, the trap is usually in one word").
- Exactly ONE worked example, similar in shape to the practice questions but not identical.
- Steps must show the actual reasoning process, what a sharp student notices and when, not just "the answer is X because Y."
- Keep underlying content conservative for the year level; the challenge is entirely in reading carefully and pattern-spotting.
- Calibrate reading level by counting, not by feel. Average about 12 to 15 words a sentence for Years 3 to 6 and no sentence over 22; Years 1 to 2 shorter again, Years 7 and up may run a little longer. At most one subordinate clause in a sentence. A student who cannot read the sentence cannot reach the thinking it is asking for.

- If the worked example is a letter-code cipher, compute it letter by letter and use ONE consistent rule (e.g. every letter +1). Re-check each letter before finalising, an inconsistent code (shifts like +1,+2,+1,-1) is broken and unusable. If unsure, use a simple constant +1 or +2 shift.
- If the worked example is a logic/deduction puzzle, make sure the clues have EXACTLY ONE valid solution. Solve it yourself before writing it down. If your clues turn out to contradict each other or allow multiple answers, discard the puzzle and write a fresh one that works.

CRITICAL: clean final steps only:
The `steps` are a polished teaching explanation, not your scratch work. NEVER include self-correction, second-guessing, or phrases like "wait", "let me re-read", "that contradicts", "actually", or "on second thought". If while solving you realise the example is flawed or you made an error, FIX the example and write clean steps for the corrected version. The student must see a confident, correct, linear explanation, never your reasoning stumbles.

`worked_example.diagram_spec` should stay null for Verbal Reasoning. For Quantitative Reasoning it may occasionally use a simple `number_line` spec if it genuinely clarifies a pattern, otherwise leave null.

Return ONLY the JSON. No prose, no markdown fences.
